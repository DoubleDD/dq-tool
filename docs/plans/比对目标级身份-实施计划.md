# 比对目标级身份字段 — 实施计划

> 状态:**已实施**(2026-09-17):V62 迁移 + 后端 resolveIdentity 推导/覆盖 + 前端向导多选与每目标收缩;confirm-mapping 载荷加可选 `identities`;common 632 测试仅 1 个 main 既有失败(RelationInferFlowTest,与本改动无关),server 69/69 全绿
> 背景:一个比对任务 = 一张基准表对多张业务表,各业务表的身份字段不一致(A 系统 code/name 对应基准 code/name,B 系统 BC/BN 对应基准 id/nm,组合身份等)。现状身份语义是任务级两个固定槽位(`compare_job.key_field`/`display_field`)+ 任务级 `match_mode`,无法支撑。

## 设计定稿(讨论结论)

核心:**身份配置下沉到目标级,且只声明「基准侧哪些字段参与判同」,目标侧列由既有 `field_mapping_json` 推导**,不另存列对应(单一事实源)。

- 任务级(向导第 1 步):`keyFields` 由单选改多选,语义从「定死身份」降级为「默认身份/身份字段并集」;`displayField`、`matchMode` 保持任务级不变
- 目标级:每张目标表的有效身份 = `identity_json`(人工显式覆盖)?? **默认推导**(任务级 keyFields ∩ 该目标映射中已连线的基准字段)
  - 只连上一个 → 自动认它为该目标身份(多数场景零配置)
  - 连上多个 → 默认组合身份(全部相等才算同一行),可人工覆盖为只用其中部分(落 `identity_json`)
  - 一个都没连 → 提交/审核时拦下
- 推导是确定性纯函数,每次执行/校验重算,与 mapping 永不双写不一致;`identity_json` 只存人工覆盖
- 运行时**不做**「挨个字段试探哪个对上算哪个」——身份在配置期确定,避免撞值错配

## 一、表结构(新迁移 V62,禁改旧脚本)

`common/src/main/resources/db/migration/V62__compare_target_identity.sql`:

- `compare_job.key_fields_json` CLOB NULL — 任务级身份字段数组(基准字段名 JSON array);NULL → 由 `key_field` 单列退化 `[keyField]`,老任务口径不变
- `compare_target.identity_json` CLOB NULL — 人工覆盖 `{"keys":["code"]}`;NULL = 按上面规则推导

两列均 `ALTER TABLE ... ADD IF NOT EXISTS`,参照 V59 写法。

## 二、后端改造(common 模块)

全部在 `CompareService.kt` / `CompareRepository.kt`,核心保持纯函数。

1. **Repository**:`JobRow` 加 `keyFieldsJson`,`TargetRow` 加 `identityJson`;读写两处同步
2. **身份解析纯函数**(新增,可单测):
   `resolveIdentity(jobKeyFields, mapping, identityJson): List<String>` — identityJson 非空用其 keys(须 ⊆ 任务级 keyFields);否则取 keyFields ∩ mapping 键(无映射时 = keyFields 全体,走按名称自动匹配老路径);结果为空抛 IllegalArgumentException
3. **组合键**:行 map 键 = 身份列值 trim 后以 `\u0001` 拼接(单列即现状);任一身份字段值为空 → 该行不参与配对(loadRows 跳过,落 MISSING/EXTRA)
4. `loadRows(:653)`:`keyColumn: String` → `keyColumns: List<String>`,select 必须包含全部身份列(身份字段恒入比对字段,与现行 keyField 口径一致)
5. `matchObjects(:2324)`:`keyField: String` → `keyFields: List<String>`;`appendCodePairs` 改为按组合身份值配对,目标侧建 HashMap 索引(putIfAbsent 保留先出现行,O(n+m),顺带替掉现在的 O(n·m) 扫描,语义不变);名称路、LEGACY、EXACT 各模式口径不变
6. `diffObjects(:2130)`:`keyField` → `keyFields: Set<String>`(身份字段对命中行恒一致的逻辑随之扩展)
7. `compareOneTarget(:575)`:开头 `resolveIdentity` 解析该目标身份 → 换出目标侧身份列(经 mapping 或按名称)→ 传组合键给 loadRows/matchObjects;错误消息点名列名
8. `normalizeMapping(:205)`/`resolveRequest(:133)`:硬约束从「映射必须含 keyField」放宽为「必须含该目标有效身份字段全部」(按 resolveIdentity 同一推导);提交载荷 `targets[]` 每项可带 `identity:{keys:[...]}|null`
9. `compare_job.key_fields_json` 写入:提交时 `keyField` 列继续写 keys 第一项(旧列不空,老读取路径不炸),`key_fields_json` 存全量;读取时 NULL 退化 `[keyField]`
10. **导出**:`object_key` 取基准侧组合键拼接;`writeRowLevelSheet` 等按任务级 keyField 取身份列处改为按该目标有效身份字段
11. **批量导入**(`CompareImportService`):locked codeField/nameField 已落 mapping,身份由推导自动生效,预期零改动;核实 `CompareMappingPrompts` 的「主键兜底」逻辑按 keyFields 第一项口径仍成立
12. 兼容铁律:`identity_json`/`key_fields_json` 全 NULL 时行为与现状逐字节一致;现有 `CompareExportFlowTest`/`CompareExportTest` 等单测原样通过;新增组合身份、目标级覆盖、推导弹空三组单测
