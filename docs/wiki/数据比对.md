# 数据比对

> dq-tool 项目文档,索引见根 [AGENTS.md](../../AGENTS.md)。

以一张基准表为准,与多个目标系统(数据源)中的对应表**先按对象身份对齐、再逐字段比对**,产出差异明细与质量报告。

**受控功能**:不在基础功能集内,授权码必须显式包含 `compare` 才可用——未授权时侧边栏隐藏入口、`/compare*` 路由守卫拦截、`/api/compare-jobs/**` 返回 403(详见 [授权码](授权码.md))。

## 任务模型

- 基准:数据源 + 库/模式 + 表(单选);对象编码字段(比对主键):基准表字段单选 1 个
- 新建向导步骤 1 用四栏级联组件 `TableCascadePicker` 选基准表:数据源 → 数据库 → 模式 → 表(选项带表注释);
  模式栏仅多库方言(SQL Server/Kingbase)动态显示,其余方言没有独立模式层、库/schema 合并落在第二栏(界面呈三栏)。
  **「数据库」栏的库清单自动应用数据源库过滤白名单**(走 `/databases`/`/schemas`,白名单由后端读取路径统一过滤,规则见 [数据源](数据源.md));步骤 2 目标侧同一个组件,规则一致
- 比对字段:基准表字段子集(含对象编码),按名称(忽略大小写)映射到目标表字段;
  **不再预选——由向导步骤 3 的字段映射连线决定:任一对比表与基准表连了线,连线基准端的字段即比对字段**,
  提交时取全部连线的基准字段并集 + 身份两字段(对象编码/对象名称恒参与),按基准表字段顺序落 `fields`;
  目标缺对象编码列提交时直接报错;缺其他比对列记「字段缺失」,该字段在命中行全部按不一致计
  (diff_json 的 value 用 `«字段缺失»` 标记)
- 对象名称(显示名)字段:**向导步骤 1 的独立单选列**(与「对象编码」列并列),默认预选「第一个文本型非主键字段」,
  决定差异明细「对象」列显示成什么;提交时兜底并入比对字段(后端要求 displayField 属于 fields,UI 层自动保证);
  提交时即解析成基准表实际列名落 `compare_job.display_field`;
  接口层留空/老任务为空时按同一规则回退,一个文本字段都没有则 object_name 落空串
  (口径收敛在 `CompareService.resolveDisplayField`,纯函数可单测)
- 目标:每个 = 数据源 + 库/模式 + 表,一任务多目标;目标行存数据源名称快照(改名/删除后仍可展示)
- 字段映射(人工连线,向导步骤 3「字段映射」):每个目标可带一份 `基准表字段名 → 目标表列名` 映射,
  落 `compare_target.field_mapping_json`(V48);**未提供 = 按字段名忽略大小写自动匹配(旧行为,老任务/老接口兼容)**;
  提供时校验逐条成立(基准字段必须存在且在 `fields` 内、目标列必须存在),且**必须映射到比对主键**(否则无法按主键对齐行,提交 400);
  执行时目标侧只认映射——未映射到的基准字段不进 select,由 `diffObjects` 记「字段缺失」按不一致计;
  目标键列取映射值。同一目标内映射是**一对一**的(一个基准字段只连一个目标列、一个目标列只被连一次)。
  差异明细页工具栏「字段映射关系」按钮弹只读连线图(`CompareMappingView`,复用 `RelationGraphCanvas` mapping 模式,
  数据源 = 任务详情 `targets[].mapping`;老任务无映射按字段名自动匹配兜底展示并给提示,不挂连线/删线事件)。
  画布交互口径(`RelationGraphCanvas` mapping 模式):节点可拖动,**拖动/增删连线/聚焦都不会触发自动重排**
  (就地重绘剥离节点 style.x/y,手动位置不被盖回;连线按 id 差集就地增删),只有工具栏「刷新」
  (底座 `customRedraw` 接管为「重新排列」)整体重建恢复自动布局,并 fitView 容纳全部节点
  (卡片常比视口高,居中到 100% 只能看见中段一截);
  点对比表标题区(不含字段行)聚焦该表 ↔ 基准表的连线,Shift+点击/Shift+拖动框选可多表聚焦
  (聚焦集合 = 底座选中集合,与单点标题同一回调口径);其余表与连线压暗、聚焦线 canvas 内 zIndex 置顶,
  压暗表与压暗连线都禁用交互——表节点 pointerEvents:none 穿透到画布,压暗线不响应悬停/点击、光标不变,
  点压暗表等于点空白取消聚焦;点基准表标题/画布空白取消聚焦;
  连线两端画实心小圆点(跨表穿过的线没有端点圆点,是否真连到该表一眼可辨);
  连线(create-edge)只认字段行上的点击,标题区不起橡皮筋;先点哪侧都行(基准↔对比两个方向均可,
  边方向归一化为 基准→对比),起点字段行钉住不随鼠标动;连线增删/变色全部关动画瞬时绘制
  (G6 v5 公开 `graph.draw()` 忽略入参固定开动画,须走 `context.element.draw`)
- 步骤条交互(向导三步数据前后依赖,`CompareNew.vue`):规则是「前一步数据没变、后一步原样保留;前一步一改、后面所有步骤清空」——
  经「下一步」校验通过的步骤记为已激活(进度 `maxStep`,步骤条高亮也跟着它走),**已激活步骤可点击回看,纯切换视图、不改任何数据;
  未激活步骤灰显禁止点击**;回看时若改了当步数据,激活进度立刻收回该步、后续步骤数据清空变灰,
  只能从该步重新点「下一步」逐层再走;第 1 步换基准表才会重新加载字段并清空后两步,
  回看时重选同一张表不动任何已填数据(`loadedTableKey` 判定;任务名不参与数据链,改动不清空后续;
  对比模式/匹配逻辑/对象编码/对象名称只是提交元数据,切换不清空后两步——主键改了没连线会在提交与画布上被拦下提示)
- 对比模式(compare_job.compare_mode,V50;向导第 1 步字段表上方为复选框「列对比」):
  **不勾选 = ROW 行级(默认,存量 NULL/缺列同此)仅比对对象身份字段、映射人工连线(现有能力);
  勾选 = COLUMN 行级+列级,身份对齐(行级)基础上逐字段比对连线的信息字段,
  字段映射由大模型预生成、人工在画布审核**(prompt 组装/解析纯函数在 `CompareMappingPrompts`,容错抽 JSON/过滤非法条目/主键同名列兜底)。
  执行引擎两种取值同一套(fields 驱动 + mapping 驱动 + 全量分页扫描),模式只影响「AI 预生成字段映射」入口与提交元数据。
  预生成端点 `POST /api/compare-jobs/mapping-suggest`(compare 受控功能门禁内):逐目标串行调 LLM(AiScene.COMPARE_MAPPING),
  单目标失败只记 note 不炸整体;未配置大模型 409 提示先完成 AI 配置。列表任务名旁与差异页信息条均有 行级 / 行级+列级 标识
- 差异类型:`MISSING`(基准有目标无)/ `EXTRA`(目标有基准无)/ `DIFF`(字段不一致)/ `SAME`(完全一致)
- 状态:`RUNNING`/`DONE`/`FAILED`/`CANCELED` 之外有 `PENDING` 待处理(V59,批量导入产物,带 pending_reason):
  **静止状态,不进执行器、不进后台任务中心**,经「字段审核」确认或「编辑」后才开跑,详见「批量导入」

## 对象匹配逻辑(界面两种口径,向导步骤 1 选择)

对比表的身份字段常与基准表对不上(同一条数据 code 一致 name 不一致、或 name 相同 code 不同),故「两条数据是不是同一个对象」由用户在新建任务时选定一套口径,一任务一套,落 `compare_job.match_mode`:

| 取值 | 界面文案 | 判定规则 |
|------|----------|----------|
| `EXACT`(默认) | 编码+名称 | **只按对象编码配对**:编码相同即同一对象,名称写法不同也算命中(名称差异按字段级 `DIFF` 体现);编码没配上的对象直接判缺失/多余,不做名称/大模型补配(最严格) |
| `CODE_NAME_LLM` | 先编码后名称+大模型归一化 | 先用编码配;编码没配上的再按对象名称配;都没配上的双侧残余交大模型按业务含义再认一轮 |
| `CODE_THEN_NAME`(旧版,界面不再提供) | 先编码后名称 | 有编码先用编码配;编码没配上的对象,再用对象名称配一轮(存量任务兼容保留,接口仍可提交) |
| 空(老任务) | 仅编码(老任务) | 只按对象编码对齐,与历史结果口径完全一致(`MatchMode.LEGACY`,前端不可选) |

> 界面文案「编码+名称」是历史叫法,**不代表名称参与配对**:除 `LEGACY` 外都要求指定对象名称字段(`requiresName`),
> 但名称只在 `CODE_THEN_NAME`/`CODE_NAME_LLM` 里作为**编码没配上时的兜底配对键**;`EXACT` 下名称只用于展示。
> 单测 `CompareMatchTest`「匹配逻辑1」用例明确:编码都对上时,第二条名称不同**仍算命中**,名称差异在字段比较里体现为 `DIFF`。

- 身份字段绑定:对象编码 = `key_field`(比对主键);对象名称 = `display_field`。
  **`CODE_NAME_LLM` 必须指定对象名称字段**(前端第 1 步拦下,后端提交 400「…需要按对象名称配对,请在「选择基准表」里指定对象名称字段」)
- 比较口径:两侧标识都 trim 后比较——**编码区分大小写**(与历史「拿编码当行键」口径一致,老任务结果不回归),
  名称忽略大小写;空值(缺失/空串)不参与配对;
  身份列为空的行(行内代理键)编码路无命中、留在残余交给名称路/大模型路,即「任意一边 code 空就用 name 匹配」;
  一个键只配一次(重复键保留先出现的行,不串行);编码配对在前、名称配对在后,便于按来源计数
- 配对的双侧对象以**基准侧键**为对象标识落 `object_key`;两侧编码/名称不一致本身会在字段级比较中体现为 `DIFF`
- 落库与展示:`compare_target.code/name/ai_matched_count` 记录三路各自命中数(三者之和 = `matched_count`),
  `compare_diff.match_by` 记录该行对象的对齐来源(CODE/NAME/LLM);差异明细给名称/AI 配对的行打「名称配对 / AI 配对」标签,
  质量报告「对象命中」列悬停展开三路命中数,任务列表有「匹配逻辑」列。老任务三列为 NULL,展示按「编码命中 = matched_count、名称/AI = 0」解读
- 对象对齐算法 `matchObjects` 为**纯函数**(编码/名称两路),单测见 `CompareMatchTest`

### 目标级身份字段(V62)

任务级两个固定槽位(`key_field`/`display_field`)撑不住「一张基准表对多张业务表、各业务表身份字段不一致」,
故身份配置下沉到目标级,且**只声明「基准侧哪些字段参与判同」,目标侧列由既有 `field_mapping_json` 推导**(单一事实源,不另存列对应):

- 任务级(向导第 1 步):`key_fields_json` 存身份字段数组(多选),语义为「默认身份/身份字段并集」;
  `key_field` 旧列继续写 keys 第一项;**NULL(老任务/批量导入)退化 `[keyField]`,口径与现状完全一致**
- 目标级:每张目标表的有效身份 = `compare_target.identity_json`(`{"keys":[...]}` 人工显式覆盖,须 ⊆ 任务级 keyFields)
  ?? **默认推导**(纯函数 `resolveIdentity`,每次执行/校验重算,与 mapping 永不双写不一致):
  任务级 keyFields ∩ 该目标映射中已连线的基准字段——只连上一个自动认它(多数场景零配置),
  连上多个默认组合身份(全部相等才算同一行),可人工覆盖为只用其中部分;
  无映射(按字段名自动匹配老路径)= keyFields 全体;**一个都没连 → 提交/审核 400 拦下(点名列出)**
- 组合键:行 map 键 = 各身份列值 trim 后以 `\u0001` 拼接(单列即现状);任一身份字段值为空的行不参与配对(落缺失/多余);
  身份字段恒入比对字段 `fields`(与现行 keyField 恒参与口径一致),`loadRows` select 含全部身份列
- 硬约束放宽:「映射必须含 keyField」→「映射必须含该目标有效身份字段全部」;
  提交载荷 `targets[]` 每项可带 `identity:{keys:[...]}`(仅人工覆盖时),响应 `CompareJobView.keyFields`/
  `CompareTargetView.identityKeys` 供编辑回填
- 运行时**不做**「挨个字段试探哪个对上算哪个」——身份在配置期确定,避免撞值错配;
  导出(行级对比明细/对象级差异判定)按该目标有效身份字段取值,`object_key` 为基准侧组合键

## 大模型归一化匹配(匹配逻辑「先编码后名称+大模型归一化」)

- 输入 = 编码/名称两路都没配上的**双侧残余对象**,每侧只带身份标识(编码 + 名称,带上字段名供模型理解);
  输出约定为「基准侧序号 → 目标侧序号」JSON 数组,prompt 组装与解析见 `CompareMatchPrompts`(纯函数,可单测)
- 分批:按「基准侧分批 × 目标侧全量残余」组 prompt,单批基准条数 = 5000 ÷ 目标侧残余数(下限 5 条),
  单请求配对数上限 5000;逐批解析、跨批去重(串行失败只跳过该批并继续)
- **同名二轮消歧**(首轮归一化之后):名称首配存在歧义时(某名称双侧都有、至少一侧 ≥2 条同名,
  见 `sameNameAmbiguousGroups`——参与对象限「未配对或按名称配对的行」,编码/大模型已配行不重配),
  把这些同名对象连同**全部比对字段取值**(经纬度/位置等)再交大模型重判哪些是同一名下的同一对象、
  哪些只是重名(prompt 见 `CompareMatchPrompts.buildSameNameRefinePrompt`);有有效新配对的组**整体重画**
  (摘除组内首轮名称配对再落新配对,来源仍记 NAME),未获配对的回落缺失/多余——解决「多个编码全空的
  同名水库按名称首配张冠李戴」的问题;未配置大模型/参与对象超上限不执行,单组失败保持该组首轮配对
- 降级(都不炸任务,残余按缺失/多余处理并在 `compare_target.error` 记说明):
  - 未配置大模型 → 说明「未配置大模型,基准 N 条 / 目标 M 条残余按未匹配处理」
  - 双侧残余任一侧超 2000 条(`LLM_RESIDUE_LIMIT`)→ 说明「残余对象过多…未做归一化补配」
  - 部分批次调用失败 → 说明「大模型归一化补配部分批次失败(原因)…」,该目标仍按编码/名称口径正常完成
- 调用计入 AI 用量统计(场景 `COMPARE_MATCH`「比对匹配」),可在 AI 用量页按场景查看

## 值比较规则

- 字符串 trim 后比较;NULL 与空串(含全空白)视为一致
- 数值字段(基准侧 jdbcType 为 NUMERIC/DECIMAL/INTEGER/BIGINT/SMALLINT/TINYINT/FLOAT/DOUBLE/REAL):
  trim 后去千分位逗号转 BigDecimal,`compareTo==0` 判定;解析失败回落字符串比较
- 显示名 object_name:取 `compare_job.display_field` 指定字段在该行的值(用户指定优先);
  未指定时取「比对字段中第一个文本型(字符型或 CLOB)非主键字段」的值,都没有则空串;
  SAME/DIFF/MISSING 行取基准行的值,EXTRA 行取目标行的值(超 500 字符写库截断)

## 取数与执行

- 复用 `dialect.pageRowsSql` 按首个身份列 orderBy 分页拉全量(pageSize 5000),内存
  `LinkedHashMap<key, Map<field, value>>` 按身份组合值分桶;行值 `rs.getObject()?.toString()`
- 单侧行数上限 50 万,超出抛 IllegalStateException,任务判 FAILED 并写明原因;
  **身份列为空的行不丢弃**:以行内代理键(`\u0002`+序号,`CompareService.NO_KEY_ROW_PREFIX`)进 map——
  编码路对它自然无命中,名称/大模型两路可把它配对(「任意一边 code 空就用 name 匹配」口径);
  身份列空行数落 `no_key_rows`(V63)并 warn 日志 + 目标说明 + 导出总览「差异原因」透出;
  差异明细的 `object_key` 对代理键回落用显示名展示(代理键本身不落库)
- 对齐口径按 `match_mode` 先算配对(`matchObjects`,再把大模型补配结果并入),最后交给 `diffObjects`
  逐对比较;配对的双侧键不等也照样逐字段比对(两侧行 map 的键已统一归一为基准字段名)
- 固定 2 线程池(线程名 compare-N,守护);进度单元 = 1(基准读取) + 目标数,stage/done_units 增量推进
- **后台任务中心**(与关系推导共用,头栏指示器 + `BackgroundTasksDrawer`):列级对比是小时级长任务,提交后离开列表页进度不丢——跟踪器 1s 轮询 `GET /api/compare-jobs/active`(瘦出行:进度百分比/阶段/目标 done-total 计数,不含比对字段清单与目标明细),终态弹全局通知(点击跳 `/compare/:id/diff` 差异明细页签);CompareTasks/CompareDiff 自行渲染到终态的任务先 `ackTask('compare', id)` 去重;compare 授权门禁同前缀,跟踪器按授权菜单裁剪(`stores/backgroundTasks.js` 的 `KIND_MENU`)——**未开放 compare 菜单的实例根本不发起该轮询**,而不是等 403 后再静默跳过(2026-09 修复:该探测曾是未授权实例每次启动必现的一条错误中心 `API_403`)
- 单个目标失败只把该 target 置 FAILED 记 error 继续下一个;基准读取失败整个任务 FAILED
- 重跑:仅 DONE/FAILED/CANCELED,tx 清空目标与差异明细后按原目标清单重建执行(字段映射随目标行一并沿用)
- 启动恢复:`recoverUnfinished()` 把残留 RUNNING 任务(及其未终态目标)置 FAILED,error 写「应用重启,任务中断」;
  PENDING 待处理是静止状态,仅残留「映射推导中」(MAPPING_RUNNING,后台推导线程随重启消亡)的转
  MAPPING_REVIEW 并记「应用重启,映射推导中断,请人工审核补线」(审核画布补线即复活),其余 PENDING 不动
  (导入批次侧另有恢复:残留 BUILDING 批次置 FAILED)

## 质量指标(compare_target)

- 对象覆盖率 = matched / base_count(base_count 为 0 记 0;base_count = 基准表实际读到的总行数,
  含身份列为空被跳过的行——这类行无法被 matched,覆盖率如实反映,跳过行有日志/差异原因透出)
- 字段一致率 = 1 − field_mismatch / (matched × 比对字段数),分母 0 记 1.0
- 数据完整率 = 目标侧已比对单元格中非空占比(列缺失按空计),分母 0 记 1.0
- 综合评分 = 覆盖率 × 0.4 + 字段一致率 × 0.4 + 完整率 × 0.2(仍落库/接口保留;报告页已按客户要求去掉该列,不再展示)

## 存储(V43,后续版本增量加列)

- `compare_job`:任务(基准信息、key_field、fields_json 比对字段 JSON 数组、**display_field 对象名称字段(V45,可空)**、

## 批量导入(Excel 一 sheet 一任务,V59)

现场动辄几十上百张表要比对、人工点选不现实的场景:上传一张 xlsx,**一个 sheet = 一个比对任务**
(按「是否基准表」列定位基准行,恰一行「是」,不要求首行;固定 `match_mode=CODE_NAME_LLM`、`compare_mode=COLUMN`),大模型只承担
字段映射推导这一件重复劳动,人做两道把关:数据源映射确认、字段映射审核。入口在任务列表「导入表格」按钮;
**未配置大模型时提交直接 409**(入口即拦、文件不落盘),不做无大模型降级——推导失败也不退回按名称
自动匹配,由人工在审核画布上补线(这正是审核存在的意义)。

### 输入 Excel 格式

- 单文件多 sheet;每个 sheet 表头 15 列(按表头名去空白定位,顺序不限,口径照 `SampleTableExcelParser`;

  表中文名称 | 表英文名称 | 是否基准表 | 对象编码字段 | 对象名称字段 | 是否纳入采集范围`;
  缺必需列表头(数据库类型/IP地址/端口/数据库名称/表英文名称/是否基准表)直接报错,整个上传失败(批次 FAILED,原件仍留档);
  解析器 `CompareImportExcelParser`(object 纯函数,XSSFWorkbook + DataFormatter)
- 逐列口径:

  | 列 | 口径 |
  |---|---|
  | 所属水利对象类别名称 | **自由文本**,不校验内置列表(客户的「供(取)水量监测点」等原样保留);仅基准行取值(任务级信息,对比行忽略),trim 后落任务 `object_category`,空则留空 |

  | IP地址/端口/数据库名称 | 连同类型一起是**定位数据源的依据**(类型 + host 小写 + port + 库名),必填 |
  | 用户名/口令 | **可选**;仅数据源在系统中不存在、需要新建时必填,两头都没有 → 该数据源标异常(可先不填导入,确认映射时发现没有对应数据源再补上重新导入)。**口令只活在内存**,批次表不落口令列(confirm 阶段重新从原件读入) |

  | 表中文名称 | 解析留档(供展示/报告),导入流程不消费 |
  | 表英文名称 | 必填(比对表名) |

  | 对象编码字段 | 基准行必填(= keyField);对比行**可空**——填了直接锁进映射(不进推导范围),没填交大模型推导 |
  | 对象名称字段 | 基准行必填(= displayField,CODE_NAME_LLM 要求);对比行可空,同上 |
  | 是否纳入采集范围 | **比对导入不读该列**(人工采集功能的列,随客户模板保留,仅参与表头定位与全空行判定) |

- sheet 级校验(违反则该 sheet 整体跳过记报告,不阻塞其他 sheet):没有表头行/缺基准行(「是」零行)/
  基准行多于一行/基准行缺身份字段/没有有效对比行;全空行跳过;「是否基准表」无法识别、缺必需列、
  端口/数据库类型无法识别的行进 SkippedRow 记报告
- **跳过原因要把行级原因带出来**(2026-09-17 修):「是」行先被行级校验(缺必需列/端口非法/类型无法识别)
  丢掉时 sheet 级原因记「基准行无效: 缺少必需列: 数据库名称」而非笼统的「缺少基准行」;「否」行全被丢掉时
  「没有有效对比行」后附首个原因。全部 sheet 无效导致整批失败时,`submit` 抛出的错误信息同时列出整 sheet
  原因与逐行原因(「…；另跳过 N 行:…」),否则用户只看到「缺少基准行」,找不到真正漏填的列
  (现场实例:库名填进「模式名称」列、「数据库名称」留空)
- 任务名 = 上传文件名(去扩展名) + `-` + sheet 名,超长截断 200;sheet 名为空/含非法字符回退
  `<文件名>-sheet<序号>`(序号 1 起);不做大模型命名,不做唯一性约束(比对任务名本就允许重复)
- 模版:`GET /api/compare-import-template` 下载(新 15 列表头 + 基准/对比两行示例);**路由刻意避开
  `/api/compare-imports/` 前缀**——同前缀静态段会被 `{id}` 路由吃掉报 400(同 `/api/sample-export-template` 先例)

### 三步流程

1. **数据源确认**:`POST /api/compare-imports`(multipart `file`,仅 .xlsx)→ 原件先落盘留档 → 解析全部 sheet →
   跨 sheet 汇总去重数据源(类型+地址+端口+库,**不含用户名**)→ 逐条匹配已建档:MATCHED 已匹配 /
   CREATE 待新建(表格有用户名口令)/ ERROR 异常(两头都没有);批次置 DS_REVIEW,前端弹映射清单。
   清单「匹配结果」列为**逐行下拉**(选项 = 系统现有全部数据源 + 「待新建(用表格连接信息实测建档)」;
   MATCHED 行默认选匹配到的数据源,其余默认「待新建」),用户可改绑到任意现有数据源——
   ERROR 行(系统没有且表格无口令)由此可改绑现有数据源而不再是异常。已建档数据源 jdbcUrl 反解不出地址的不参与匹配
   (共享 `DatasourceKeyMatcher`,抽样导出侧用含用户名的全量 key,比对导入只用定位 key)
2. **确认并建任务**:`POST /api/compare-imports/{id}/confirm`(仅 DS_REVIEW,否则 409)——**异步**:
   立即返回 `{ok:true}` 转后台执行(批次 BUILDING),前端 2s 轮询批次详情到 DONE/FAILED 后从 `jobIds`
   拿任务清单。**可选 body `{"mapping": {"<ds_report 行 key>": <数据源 id 或 null>}}`** 提交用户逐行选择:
   值非 null = 改绑到该现有数据源(id 不存在 400,校验在转后台前完成、不消费 DS_REVIEW 状态),
   直接绑定跳过建档,报告 action 记 REBOUND;值 null = 该行「待新建」,即使地址能匹配已建档也强制走建档;
   不带 body/空映射 = 全部按原匹配结果(向后兼容),键不在报告里的映射项忽略。
   后台只做秒级动作即置 DONE(**confirm 不再阻塞实测与大模型**):待新建数据源**同步插行建档**
   (有口令的 conn_status 留空=未实测,连接实测挪到批次 DONE 后的映射阶段;无口令的照旧直接标 ERROR),
   分组「比对批量导入」,名称取「实际系统或模式描述(数据库名称)」(描述空则只用库名)、重名加 ` (2)` 后缀;
   **异常数据源也建档**(conn_status=ERROR,便于在数据源页修复后复活任务);
   已建档但 conn_status=ERROR 的不自动复测;然后逐 sheet 建任务(固定 4 线程池,不做暂停/恢复):
   - 身份字段(code/name)表格给了的锁定进目标 mapping、从推导范围剔除;基准表校验与字段归一挪后台,
     phase 1 不连业务库(待新建数据源可能连不上,避免拖住批次)
   - 涉及异常数据源(无法建档/无口令未实测/绑到 ERROR)→ PENDING + DS_ERROR,**不进推导队列**;
     基准数据源无法建档时整任务不建、报告记 NOTE;其余一律 PENDING + **MAPPING_RUNNING**(映射推导中)
   - 所属水利对象类别名称取基准行表格原值落 `object_category`(自由文本不校验、不调大模型);任务名 = 文件名-sheet 名(不调大模型)
   - **库/schema 落库前按数据源方言归一**(`CompareService.normalizeLocation`):单库方言(MySQL 等)存
     schema=库名、db 空,与手工建任务同口径——早期直接存表格原值(库名进 db、schema 留空)会让前端
     编辑向导/字段审核按 `schemas/{schema}/` 拼出 `//` 路径 404;存量任务由任务详情/列表视图层
     (`toJobView`/`toTargetView`)同一函数归一兜底,无需数据迁移
   - **批次 DONE 后映射线程池(固定 4 线程,与建任务池分离)逐任务推进**:先实测任务涉及的待新建数据源
     (**批次内同 dsId 去重只测一次**,单条 20s 与抽样导出同口径),实测失败 → 数据源转 ERROR、任务转
     DS_ERROR 记 error 不推导;连通后做基准表校验(表/身份字段缺失 → 整任务 IMPORT_ERROR 记 error,
     身份字段按表格原值兜底)并归一实际列名,再逐目标串行调大模型推导(AiScene.COMPARE_MAPPING;
     推导失败/映射不含主键只留锁定项并记目标说明,由人工在审核画布上补线;合并时锁定项优先),
     完成转 **MAPPING_REVIEW**(映射一律要人审);整任务意外异常转 IMPORT_ERROR 记 error
   - 重启恢复:残留 BUILDING 批次置 FAILED(「应用重启,导入建任务中断」);残留 MAPPING_RUNNING 任务
     由 `CompareService.recoverUnfinished` 转 MAPPING_REVIEW(见「取数与执行」启动恢复;各清各的不重复)
3. **人工审核开跑**(归任务列表,交互见 [前端页面与按钮逻辑](前端页面与按钮逻辑.md)):「字段审核」弹可编辑
   映射画布 → `confirm-mapping` 校验落库后 PENDING→RUNNING;或「编辑」进向导 `?edit=<jobId>` 逐步改 →
   `PUT /api/compare-jobs/{id}` 更新(仍 PENDING)后再回列表经「字段审核」开跑

### 待处理(PENDING)状态机

- `compare_job.status` 新增 `PENDING`(待处理),带 `pending_reason`:`DS_ERROR` 数据源异常 /
  `MAPPING_RUNNING` 映射推导中(连接实测 + 字段映射后台推导进行中,审核/编辑/直启均暂不可用)/
  `MAPPING_REVIEW` 映射待审核 / `IMPORT_ERROR` 导入异常(基准表校验未通过,需「编辑」修正)
- **PENDING 是静止状态**:不进执行器(`run` 只接 RUNNING)、不进后台任务中心轮询
  (`/api/compare-jobs/active` 口径不变只跟 RUNNING)、`recoverUnfinished()` 只清 RUNNING 残留、
  把残留 MAPPING_RUNNING 转 MAPPING_REVIEW,其余 PENDING 不动;
  删除/归档对 PENDING 放行(删除不加 409;MAPPING_RUNNING 任务被删时,后台映射线程回写发现任务已不在即放弃)
- 出口仅两个:`POST /api/compare-jobs/{id}/confirm-mapping`(校验口径同 submit:映射必须覆盖该目标有效身份字段全部、
  基准字段在 fields 内、目标列存在;全量替换各目标 mapping 后 PENDING→RUNNING 进执行器;
  **也是 DS_ERROR 任务的复活出口**——先在数据源页修复连接再确认,确认时重读两侧字段重验)与
  `PUT /api/compare-jobs/{id}`(向导编辑提交:tx 内替换 job 元数据 + 删旧 targets 重建,保持 PENDING 与
  import 溯源列不动,**pending_reason 归一 MAPPING_REVIEW**;编辑不做限制——match_mode/compare_mode
  随请求改,与终态任务编辑同口径);**MAPPING_RUNNING 时两个出口连同服务层 start() 一律拒绝**(映射未出,没得审),
  映射线程结束(MAPPING_REVIEW/DS_ERROR/IMPORT_ERROR)后才可操作
- 服务层 `CompareService.start()`(仅 PENDING 且非 DS_ERROR 直启)暴露为 `POST /api/compare-jobs/{id}/start`:
  编辑向导「保存并比对」在 PUT 保存成功后调它直启,省掉回列表再点「字段审核」一圈;
  审核弹窗「确认并开始比对」仍走 confirm-mapping 一端完成

### 原件留档与批次存储

- 上传字节先写 `数据目录/compare-imports/batch-<id>/<原文件名>`(批次插行拿 id 再写文件,照
  `sample-exports/task-<id>/` 目录惯例;文件名原样保留、仅去路径分隔符防 `../` 注入,一批次一目录同名不冲突)

## API

- `POST /api/compare-jobs` 提交;body `{name, baseDatasourceId, baseDb, baseSchema, baseTable, keyField, fields[], targets[{datasourceId, db, schema, table, mapping?}], displayField?, matchMode?}` → `{jobId}`
  (`matchMode` 可省略 = `EXACT`;非法值 400「非法匹配逻辑」;`CODE_THEN_NAME`/`CODE_NAME_LLM` 未给出可用 `displayField` 时 400;
  `displayField` 可省略;填了但不在 `fields` 内直接 400「对象名称字段必须在比对字段内」;
  `targets[].mapping` 为 `{基准字段名: 目标列名}` 的对象,可省略;给了就必须含比对主键,映射到不存在的列/字段直接 400)
- 任务视图 `CompareJobView.matchMode`、差异明细 `CompareDiffRow.matchBy`(CODE/NAME/LLM,老数据 null)、
  目标视图 `CompareTargetView.code/name/aiMatchedCount`(老任务按编码命中 = matchedCount 回读)一并返回
- 目标视图 `CompareTargetView.mapping` 回读已落库的映射(基准表实际列名 → 目标表实际列名),未指定时为 null
- 任务视图补 `pendingReason`(仅 PENDING)/`objectCategory`/`importId`/`importFileName`
  (按 import_id 左联 compare_import 取来源文件名,向导手工建为 null;见「批量导入」)

## 导出格式(对照客户既有核对表)

- **sheet 1「总览」**(固定第一个 sheet):表头 `表中文名 / 表英文名称 / 所属系统 / 条数 / 数据最新更新时间 /
  与基准差 / 匹配编码数 / 匹配对象数 / 差异条数 / 差异原因`;第 1 行为基准表本身(`与基准差`/`匹配编码数`/
  `匹配对象数`/`差异条数` 留空,`差异原因` 写 `基准表(不参与差异统计)`),其后一行一个比对目标。
  「匹配对象数」为本工具追加列——客户核对表成表时只有编码一路匹配,现有多路配对后总数单列,不占用「匹配编码数」。
  **改动本 sheet 任何一列前,先读这张表与后面「差异条数」「数据最新更新时间」两节的口径说明**:

  | 列 | 口径(实现见 `CompareService.buildOverviewRows`) |
  |---|---|
  | 表中文名 | 该侧表的表注释,取不到留空 |
  | 表英文名称 | 基准行 = `compare_job.base_table`;目标行 = `compare_target.table_name` |
  | 所属系统 | `table_system` 按「数据源+库+schema+表」登记的系统名;未登记回落该数据源名快照,数据源已删留空 |
  | 条数 | 该侧表**实际行数**:目标行 = V44 `compare_target.target_count`(比对时实际读到的总行数,含多余行与身份列为空的代理键行);老任务该列为 NULL 时用 `matched_count + extra_count` 兜底,仍无留空;基准行 = 各目标 `base_count` 的最大值(同为实际读到的总行数口径) |
  | 数据最新更新时间 | **比对执行时采集的快照**(非导出时现查):基准行取 `compare_job.base_data_updated_at`,目标行取 `compare_target.data_updated_at`;详细探测口径见下方专节;老任务、无可用时间字段、取数失败、大模型未配置都留空 |
  | 与基准差 | 目标行数 − 基准行数(基准行数缺失时用各目标自报的 `base_count` 兜底);两侧任一为空留空;基准行留空 |
  | 匹配编码数 | `compare_target.code_matched_count` = 编码路(第一路)命中的对象数;老任务未采三路来源计数时按「编码命中 = `matched_count`」解读 |
  | 匹配对象数 | `compare_target.matched_count` = 双侧都存在的对象总数(SAME + DIFF,编码/名称/大模型三路之和) |
  | 差异条数 | **数量差异 = 缺失对象数 + 多余对象数**(见下方专节,**最易改错的一列**):总览只做行级数量对比,属性差异(编码不一致、字段值不一致)不计,在「行级对比明细」与各目标明细 sheet 体现 |
  | 差异原因 | 按差异构成自动拼写(从前往后拼):`基准有目标无的对象 x 条` / `目标有基准无的对象 y 条` / `编码不一致的对象 n 条` / `行数相差 d(目标 T / 基准 B)` / `身份列为空 n 行(仅按名称/大模型配对)`(V63,有身份列空行才拼)。**不含字段级差异统计**(客户核对表口径,字段级差异看「字段级差异汇总」与各目标明细 sheet):字段不一致只起两个作用——阻止写「与基准完全一致」,以及仅存在字段级不一致(对象级三项全零)时写定性说明 `存在字段级不一致(见字段级差异汇总)`;缺失/多余/字段不一致三项都为 0 **且无身份列空行**时写 `与基准完全一致`;目标未完成(非 DONE)写 `比对未完成(状态):错误`;导出后可人工补充 |

  **差异条数的口径(数量差异 = 缺失 + 多余;勿把属性差异算进来)**

  - 计算公式:**差异条数 = `missing` + `extra`**(`CompareService.objectLevelDiffs`,数据来自该目标 `compare_diff` 里全部非 `SAME` 行):
    - `missing` = `diff_type='MISSING'` 行数 —— 基准有、目标无的对象
    - `extra` = `diff_type='EXTRA'` 行数 —— 目标有、基准无的对象
  - 总览是**行级数量的对比**,不看属性差异:配对上但编码对不上的对象、字段值不一致的对象,
    **都不计入本列**——前者在「行级对比明细」sheet 逐对象列出、后者在各目标明细 sheet 逐字段展开;
    「差异原因」里仍会写明 `编码不一致的对象 n 条` 供人工核对
  - 数量口径天然有界:差异条数 ≤ 两侧行数之和,不会出现"差异比对象还多"的怪数字
  - 基准行本列留空(基准不参与差异统计)
  - **与「行级对比明细」sheet 的关系**:行级 sheet 行数 = 差异条数 + 编码不一致的对象数
    (行级 sheet 列 `MISSING`/`EXTRA`/编码不一致的 `DIFF` 行,编码一致的 `DIFF` 行哪怕名称不同也不列,
    判定见 `CompareService.hasIdentityDiff`);差异条数 ≤ 行级 sheet 行数,两者不要混为一个数
  - 身份判定仍服务两处:行级 sheet 的列入判定 + 差异原因的「编码不一致的对象 n 条」分量。
    **身份字段只认比对主键(对象编码),不认对象名称**:编码相同即同一个对象,名称、经纬度等其它字段
    取值不同属**字段级差异**。为什么名称不算身份:`EXACT`(界面默认)与 `CODE_THEN_NAME` 的第一路都是
    **按编码配对**,编码相同、名称写法不同的对象本来就是同一个对象(例:基准 `大西山` ↔ 目标 `大西山水库`)。
    编码不一致只计**两侧编码都非空且不同**的对象(典型即「按名称/大模型兜底配上、但双方编码对不上」);
    **一侧编码为空是「编码缺失」,属字段级差异(明细照常展开),不计**——否则整表无码的目标会把所有配对
    计成编码不一致,数量超过对象总数。新契约按 `matched` 标志判定(matched=false 且基准/目标取值都非空);
    无 `matched` 标志的老快照回落「编码值非空且 ≠ object_key」旧口径
  - 单测兜底:`CompareExportTest.行级对比明细列对象级差异行且总览差异条数只看数量差异`
    (断言「行级 sheet 列编码不一致对象,但总览差异条数只数缺失+多余」)、`CompareExportFlowTest`
    (真实 MySQL:5 条仅名称改动的对象不进行级明细,差异条数 = 缺失 3 + 多余 4 = 7)

  **数据最新更新时间的口径(比对执行时采集的快照,导出只读快照)**

  - 基准表在比对读基准全量前采集、目标表在读目标全量前采集,分别落 `compare_job.base_data_updated_at`
    与 `compare_target.data_updated_at`(V60);重跑 `clearResults` 清基准快照、目标行重建归零;
    老任务无该快照(NULL)导出留空
  - 时间字段探测三级口径(`CompareTimeFieldPrompts`,命中后对该列执行 `dialect.maxValueSql` = `SELECT MAX(列)`):
    ①名称/注释命中的 **update 类**(`update_time`/`updatetime`/`gmt_modified`/「更新时间」「修改时间」…),
    ②没有 update 类才用 **create 类**(`create_time`/「创建时间」…),同类里日期时间类型字段优先于其它类型;
    ③名称/注释都没命中时,**未配置大模型直接留空**,配置了则把该表字段清单(名称/类型/注释)交大模型语义挑
    「最新修改时间」字段(AiScene.COMPARE_TIME;回答 `NONE`/解析不出也算没有)
  - 时间族统一格式化为 `yyyy-MM-dd HH:mm:ss`;无合适字段、取数失败、未配置大模型/调用失败一律留空,
    只记 debug 日志,**绝不影响比对主流程**
- **sheet 2「行级对比明细」**(固定第二个,始终生成):一行一个「对象 × 比对目标」的行级差异,
  **首行即表头**——`基准表英文名 / 基准表中文名 / 基准编码字段 / 基准编码 / 基准名称字段 / 基准名称 /
  业务表英文名 / 业务表中文名 / 业务表编码字段 / 业务表编码 / 业务表名称字段 / 业务表名称 / 差异说明 / 差异类型`
  - 表中文名 = 表注释(取不到留空);编码/名称字段列 = 任务比对主键/显示名字段(基准侧)与其在目标表的
    映射列(业务侧:显式映射取人工连线到的目标列,无映射按基准字段同名,与 sheet 3「业务表字段」同口径),
    与行取值无关恒填;显示名未配置(老任务)时两侧名称字段列留空
  - 编码/名称取双侧各自取值:DIFF 行业务侧优先取 `diff_json` 里
    目标侧真实值(靠名称/大模型配上的对象两侧编码不同,差异照常体现;老紧凑格式没有该字段快照时
    回落基准侧);MISSING 行业务侧留空、EXTRA 行基准侧留空
  - 只列对象级差异的行:**身份字段取比对主键(对象编码)**——DIFF 行两侧编码一致的直接跳过
    (名称等字段取值不同属字段级差异,在各目标明细 sheet 体现),按名称/大模型兜底配上的(编码不同)才列出;
    MISSING/EXTRA 行始终列出
  - 差异说明:DIFF 只展开身份字段(编码/名称)的差异(字段名取基准表注释;其余字段的不一致属
    列级口径,见 sheet 3 与各目标明细 sheet),MISSING/EXTRA 写`基准有目标无`/`目标有基准无`
  - 差异类型(末列):按 `compare_diff.diff_type` 中文化,取值 **不一致(`DIFF`)/ 缺失(`MISSING`)/
    多余(`EXTRA`)**,与 sheet 3 的三分类同口径(均相对基准而言),便于导出后直接按类型筛选
- **sheet 3「字段级差异汇总」**(固定第三个,始终生成):一行一个「比对目标 × 基准字段」,
  **首行即表头**——`业务表英文名 / 业务表中文名 / 基准表字段 / 字段中文 / 业务表字段 / 业务表字段中文 / 差异数量 / 缺失 / 多余 / 不一致`
  (数量列为数值)
  - **只列与该业务表有连线的字段**:任务带显式字段映射(第三步人工连线)时只列映射键对应的基准字段,
    未连线的基准字段(比对时对该目标按「字段缺失」计)属噪音不再列出;
    无映射(按名称自动匹配,老任务)时列全部比对字段
  - 业务表字段 = 映射里该基准字段连到的目标列名;无映射按基准字段同名(自动匹配口径);
    业务表字段中文 = 目标表该列注释(无注释/目标表无此列都留空,不回落字段名)
  - 不一致 = 该字段在 DIFF 行里的不一致次数(口径同 `FieldDiff.isMismatch`,含目标缺列);
    缺失/多余 = 该目标的 MISSING/EXTRA 对象数(对象级差异,整行缺失/多余即每个比对字段都缺/多,同目标各字段同值)
  - 差异数量 = 缺失 + 多余 + 不一致 三类合计;行 = 连线字段(无差异字段也列出,计 0),
    差异里出现过的其余连线字段兜底追加在末尾
- **sheet 4「数据级字段对比差异总览」**(固定第四个,始终生成):按数据行聚合的字段对比统计,
  **一行一条数据(对象)**,只给数量、不精确到具体字段(逐字段取值看 sheet 5「列级对比明细」与各目标明细 sheet)
  - **首行即表头**:对象编码/对象名称(动态列名,与各目标明细 sheet 同口径)+ `基准表字段数` +
    每目标三列 `{所属系统}对比字段数 / {所属系统}相同字段数 / {所属系统}不同字段数`
    (所属系统与总览同口径,动态取名——表头随任务的比对系统变化)
  - 行集合:有差异的对象(任一目标存在 `DIFF`/`MISSING` 行;多余 `EXTRA` 对象不属基准侧,不展开)
  - `基准表字段数` = 任务比对字段总数(整表恒同);
    `对比字段数` = 该系统参与比对的字段数(显式映射 = 连线字段数,无映射 = 基准表字段数);
    `不同字段数` = 比对字段中不一致的个数(该对象在此系统整行缺失 = 全部比对字段;未连线字段的
    「字段缺失」不计入——那是未比对而非不一致);`相同字段数` = 对比字段数 − 不同字段数;不同字段数 > 0 标红
- **sheet 5「列级对比明细」**(固定第五个,始终生成):所有比对系统的逐字段取值**横向合并**成一张宽表,
  一行一个「对象 × 基准字段」,多系统并排逐字段对照取值
  - **两行表头**:首行 对象编码/对象名称(动态列名,与各目标明细 sheet 同口径)+ `基准字段名 / 基准字段中文 / 基准表值`
    共 5 列;右侧每个比对系统 4 列
    `{所属系统}业务表字段名 / {所属系统}业务表中文 / {所属系统}业务表值 / 差异原因`(所属系统与总览同口径,动态取名);
    第二行显示各侧表定位 `[库名][schema][表名]`(schema 为空省略该段,基准侧写在前 5 列首格,各系统写在其 4 列首格);
    左侧 5 列与两行表头**冻结**(`createFreezePane(5, 2)`,横向/纵向滚动时身份、基准列与表头不跟随)
  - 行集合:有差异的对象(任一目标存在 `DIFF`/`MISSING` 行)× 各系统比对字段的**并集**(保持任务字段顺序):
    显式映射的任务,该系统比对字段 = 连线字段(未连线 = 未比对);无映射(按名称自动匹配)的任务 = 全部比对字段
  - 某字段在该系统未比对(未连线):字段名列写「无此字段」,中文/值留空,差异原因写「未比对(无此字段)」;
    该对象在此系统整行缺失:业务表值留空,差异原因写「基准有目标无」并标红;
    不一致:基准表值与该业务表值两格标红,差异原因与各目标明细 sheet 同口径(文本不一致/业务表无此字段);
    一致:业务表三列照常填(取值与基准相同),差异原因留空
  - 多余(`EXTRA`)对象不属基准侧任何行,不在本表展开(各目标明细 sheet 仍逐行列出)
- **sheet 6…**:总览里有几条差异数据(即几个比对目标)就跟着几个明细 sheet,sheet 名 `序号_表名_数据源名`
  (`序号` 与总览行顺序一一对应);每个 sheet 装该系统**全部**差异,采用客户核对表的**字段级**口径:
  - **首行即表头**(无上下文/图例行):最左侧为业务表定位列「业务系统名称/库/模式/表名/表中文名」
    (整 sheet 同值逐行重复;**「模式」按目标数据源方言动态显示**——多库方言(SQL Server/Kingbase)
    才有独立模式层,单库方言不出该列,故定位列 4~5 列)+ 对象编码/对象名称
    (取基准表字段注释做中文列名,无注释回落字段名,无显示名字段时名称列为「对象名称」)+
    基准表块(`基准表字段/字段中文/基准表值`)+ 业务表块(`业务表字段名/业务表中文/业务表值`)+ 末列「差异原因」
  - 其后**一行一个「对象 × 字段」**:DIFF 行逐不一致字段各出一行,两侧块分别填字段英文名、
    中文注释(无注释留空)、取值——业务表字段名按任务字段映射还原目标列名(无映射按同名);
    差异格**红底高亮** = 基准/业务两个取值格标红。
    **业务表没有该列的字段(「字段缺失」按不一致计的)不在本 sheet 落行**——那是两侧表结构差异、
    不是基准与业务表之间的数据差异;整行只剩这类字段的对象在本 sheet 也不出现(该差异仍计入总览的
    差异原因与质量报告口径);
    MISSING/EXTRA 整行缺失/多余按 `diff_json` 整行快照**逐比对字段展开**(该对象的全部比对字段都缺/多,
    一字段一行)——MISSING 基准块照常填、业务表值留空,EXTRA 反之,缺失侧取值格与差异原因标红,
    差异原因写`基准有目标无`/`目标有基准无`(老数据无字段级快照时兜底一对象一行:字段六列留空、整行标红)
- `compare_diff.diff_json` 为**整行快照**:DIFF/MISSING/EXTRA 三类行每个比对字段各一条,并带显式
  `matched` 标志;`value` 一律存**该字段的目标真实值**(一致字段也有值),该侧确实不存在的值为 null。
  DIFF 行 `matched` 标定是否一致;MISSING 行 base 齐备、value 全空且 `matched=false`;
  EXTRA 行 base 全空、value 齐备且 `matched=false`。导出据 `matched` 逐不一致字段展开成行,
  MISSING/EXTRA 行则逐比对字段全量展开(明细 sheet 与「列级对比明细」同口径)。
  前端字段级展开**每格显示真实值**(空侧显示「(空)」),问题格整格底色高亮:DIFF=不一致字段目标格、
  缺失=目标整列(空侧)、多余=基准整列(空侧);报告问题字段排行按 `matched` 统计。
  **老数据兼容**:`matched` 缺失的旧数据/中间版本按旧契约「value 非空 = 不一致」解读(`FieldDiff.isMismatch`),
  老任务(只有不一致字段的紧凑 diff_json)仍能正常展示与导出
- 「先编码后名称+大模型归一化」下**靠名称/AI 配上的对象两侧编码不同**:`object_key` 取基准侧编码,
  编码字段本身的不一致照常展开成字段级明细行;按名称/AI 配对的行前端打「名称配对 / AI 配对」标签
  (`compare_diff.match_by`),导出按字段级行输出双侧真实值
- 明细行数超 `CompareService.MAX_ROWS_PER_SHEET`(100 万行,Excel 单表上限兜底)时截断并在 sheet 内追加说明;
  系统数超 `CompareService.MAX_SHEETS`(65530)时导出报错
- 表中文名/所属系统/字段注释的取数:按「数据源 + 库 + schema」预取(目标 schema 用 `compare_target.schema_name`
  快照,不能只用库名推——MySQL 场景 schema=库名);元数据回源失败、`table_system` 未登记、字段无注释都静默降级
- 格式由单测兜底:`CompareExportTest` 覆盖总览行口径(条数/与基准差/差异原因/老任务兜底)与 xlsx 结构
  (首 sheet「总览」、固定第二 sheet「行级对比明细」只列编码不一致的对象(九列双侧口径追加末列差异类型
  不一致/缺失/多余)、
  固定第三 sheet「字段级差异汇总」
  按「目标 × 基准字段」统计差异数量并拆 缺失/多余/不一致(含「业务表字段中文」取目标列注释、无注释留空)、
  固定第四 sheet「数据级字段对比差异总览」一行一条数据(按系统给 对比/相同/不同字段数,不同 > 0 标红)、
  固定第五 sheet「列级对比明细」所有系统逐字段取值并排(两行表头、第二行为各侧表定位 `[库名][schema][表名]`、左侧 5 列冻结、比对字段取各系统并集、未比对写「无此字段」)、
  总览几条差异数据就几个明细 sheet、序号对应、
  该系统全部差异都在同一张 sheet 内、字段级行(定位列 4~5 列(模式按方言动态)+ 对象编码/名称 + 基准/业务两块各三列 + 差异原因)、
  DIFF 逐不一致字段展开且业务表无此字段的字段行不落(整行只剩这类字段的对象整行不出现)、缺失/多余按整行快照逐比对字段展开、差异格红底:DIFF 两个取值格/缺失多余标缺失侧取值格与差异原因);
  `CompareExportFlowTest` 用 Testcontainers 起真实 MySQL 跑完整比对链路
  (真实行数落库 + 表注释/所属系统/字段注释取数);`CompareMatchTest` 覆盖三种匹配逻辑的配对口径、
  老任务兼容、prompt 组装与响应解析容错、大模型补配的限额/未配置/调用失败降级

## 测试环境

现成的双库测试环境见 [docker-test-env/compare-mysql/README.md](../../docker-test-env/compare-mysql/README.md):
一个 Docker MySQL 8.0(端口 3307)内建 `reservoir_base`(国标规范基准库,100 条水库)与
`reservoir_vendor`(三方厂商脏库,101 条),数据固定可复现,预置
**缺失 3 / 多余 4 / 差异 5(不一致字段 7 处)**;`verify.sh` 一键自检。
新建任务时目标数据源不再排除基准数据源(基准组合即「数据源+库+模式+表」全同才禁止作为目标),
但本环境的基准库与厂商库是两个 database,把同一实例注册成两条数据源(分别指向两个库)选库更直观。
