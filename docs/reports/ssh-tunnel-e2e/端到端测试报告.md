# SSH 隧道连接数据库 — 端到端测试报告

- **测试日期**:2026-09-07
- **被测版本**:1.9.8(开发模式 `:server:run`,common 内核 + Javalin 壳)
- **测试方式**:Docker 容器化端到端(真实 sshd 跳板机 + 真实 MySQL 8 + 完整 HTTP API 链路:授权激活 → 测试连接 → 数据源落库 → SQL 控制台 → 扫描任务 → 删除清理)
- **测试结果**:**12 项用例全部通过(12 PASS / 0 FAIL)**

## 1. 测试环境

| 组件 | 说明 |
| --- | --- |
| 容器运行时 | 本机 Docker(OrbStack) |
| 专用网络 | `dq-ssh-e2e`(bridge),测试后已删除 |
| `dq-e2e-mysql` | `mysql:8.0`(8.0.46),网络别名 `mysql` / `db.dq-e2e.invalid`,**不暴露宿主机端口**;预置库 `dqtest`(users 3 行含 1 个 NULL email、orders 4 行),root 密码 `Root@Test123` |
| `dq-e2e-sshd` | `linuxserver/openssh-server`,宿主机 `12222` → 容器 `2222`;用户 `tester`/`testpass`,密码 + 公钥双认证;按项目已知坑用 `custom-cont-init.d` 脚本把 `AllowTcpForwarding no` 改为 `yes` 并 HUP sshd |
| dq-tool 实例 | 宿主机端口 `10099`,独立数据目录 `.ssh-e2e/data`(不污染开发用 `data/`),`make dev-headless` 同等方式启动 |
| 授权 | `scripts/LicenseKeygen.java` 用仓库内 `license-private.key` 现场签发(客户「内部测试」,30 天) |

拓扑(与 `SshTunnelIntegrationTest` 同一断言思路:目标主机名只有跳板机能解析,查询成功即证明流量走了隧道):

```
宿主机 (macOS)
  │  HTTP :10099
  ▼
dq-tool server ──SSH(127.0.0.1:12222,tester)──▶ dq-e2e-sshd ──▶ db.dq-e2e.invalid:3306
  │  JDBC 直连 127.0.0.1:<本地转发端口>            (跳板机)         (dq-e2e-mysql,docker 网络内)
  └─ 对照:不经隧道直连 db.dq-e2e.invalid:3306 → Communications link failure
```

关键设计:JDBC URL 使用 `jdbc:mysql://db.dq-e2e.invalid:3306/dqtest`。该域名从宿主机不可达
(本机代理 fake-ip 会假装接受 TCP 但无 MySQL 协议响应),只有跳板机容器能通过 docker 网络别名解析到真实 MySQL。

## 4. 关键发现与已知问题

1. **扫描默认 `genDoc=true`,未配置大模型时任务在 99% 停留约 80 秒**:扫描本身秒级完成,但 ScanDocService
   尝试生成表描述,LLM 调用超时熔断后才把任务置 DONE。功能正确(熔断+跳过符合设计),但用户感知上
   「扫描卡在 99%」约 1 分 20 秒。建议:未配置大模型时前置跳过入队,而非等调用超时。
2. **一次性隧道关闭时 sshj 打 ERROR 级噪音日志**:`StreamCopier: In pipe ... Disconnected` /
   `<<copyDone>> woke to: ...`,是 `CloseableTunnel.close()` 正常断开引发的竞态,不影响功能,
   但会污染错误日志聚合(系统诊断页)。建议降为 DEBUG。
3. 本机代理 fake-ip 环境会拦截任意域名的 TCP 连接(`nc -z` 假成功),做「主机名不可解析」类断言时
   应以协议层失败(JDBC `Communications link failure`)为准,不能信 TCP connect 结果。
